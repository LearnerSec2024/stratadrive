## StrataDrive governance

GitHub is the authoritative repository. Azure Pipelines validates GitHub source independently; never create a second authoritative code repository.

- Do not deploy, publish, merge, provision resources, or change external infrastructure/service settings without explicit owner approval for that action.
- Do not access production secrets, customer records, production databases or production-capable connectors. Use synthetic data and local test targets only. Ignored files are not permission boundaries.
- Implement only an approved task packet. The owner approved `docs/iterations/1b-enquiry-packet.md` on 2026-10-25: local synthetic enquiry form/POST API, private database migration/role, guarded development/test setup and independent validation. Earlier 1A preview and 1B Compose setup remain approved. No cloud linking/provisioning, live reservations, notifications, product authentication, real customer data or deployment are approved. Preserve the packet's exclusive file ownership; root integrates shared contracts/configuration and generated schema.
- Preserve pre-existing user changes. `next.config.ts` was dirty before 0A and is outside the approved foundation write set.
- Planner and Critic are read-only roles. Tester writes only assigned tests/configuration/fixtures after approval; Developer writes only its assigned paths. No reviewer may silently fix the implementation under review.
- Agent names and prompts do not enforce access. Custom agents inherit parent permissions. Use a separate read-only parent session or filesystem boundary for enforced reviewer isolation; disclose when only procedural restrictions are available.
- Assign one writer per file with a baseline commit and exact path ownership before editing. Serialize shared manifests, lockfiles and configuration. Separate worktrees reduce interference but do not enforce permissions or prevent semantic conflicts.
- The orchestrator alone integrates changes. Review and test the integrated candidate; changes invalidate affected evidence. Do not weaken independent tests or contracts to make implementation pass.
- Link approved business requirements to technical/nonfunctional requirements, API operations (or justified N/A), test IDs and execution evidence. Planned tests and an empty API scaffold are not verified business coverage.
- Keep the canonical `contracts/openapi.yaml` and `postman/` collection/environment aligned as APIs evolve. Every approved API addition, change or removal must update affected operations/schemas/examples/status/access rules, Postman requests/examples/assertions and source identity, applicable environment values, generated schemas/visual reference, manual coverage and the current workbook's Start Here API testing section in the same change. Validate the affected artifacts and record actual evidence before handoff. Preserve prior workbooks/results and in-progress Postman key/receipt state; see `contracts/README.md`, `postman/README.md` and `docs/agent-workflow.md`.
- No production credentials or deployment connections belong in either CI provider. Required checks must fail on errors and source-identity mismatches.
- Every functional increment requires an owner local visual/manual review handoff: verified startup commands, working directory, exact URLs, safe setup and synthetic inputs, checklist with expected results, known limitations, and shutdown/reset steps. Record explicit owner acceptance separately from automated results; never mark a feature accepted on the owner's behalf. See `docs/manual-testing.md`.
- Starting with Iteration 1B, every iteration handoff must save an Excel workbook at `tests/manual/iteration-<id>-manual-tests.xlsx`. The 1B workbook is the cumulative baseline of all features delivered through 0A/1A/1B. Include feature purpose, numbered manual steps, expected results and editable human result/notes/tester/date fields. Future workbooks carry forward the applicable baseline/regression coverage and add or revise iteration changes. Preserve earlier workbooks and recorded results; initialize each new review's manual results as Not run and owner acceptance Pending. Verify the saved workbook and confirm its path at handoff. See `tests/manual/README.md`.
- Each manual-test workbook begins with a `Start Here` tab containing the ordered prerequisites, working directory, conditional dependency installation, startup commands for all required services, terminal guidance, exact URLs, readiness checks with expected results, recovery and shutdown steps. Include an API testing section with canonical contract and Postman collection/environment/guide references, import/target/request order, expected outcomes, synthetic data, retry and cleanup guidance. Keep this first tab current for each iteration and preserve recorded test results when updating it.
- Standing iteration QA rule: before closing any development iteration or major feature delivery, review the modified routes/components/migrations; append new cases with the next sequential category IDs; revise shifted UI/contract steps; update Playwright execution guidance for changed specs/tags/modes; synchronize feature-to-test traceability and index counters (Total Steps, Pass, Fail, Not Run); and provide an exact Python (`openpyxl`/`pandas`) update snippet or complete formatted update table. Preserve prior results and distinguish execution from acceptance.
- The owner-approved QA workbook sequence is Contract Tests (`CT`), API Tests (`API`), Functional UI Tests (`UI`), Usability & a11y Tests (`A11Y`), Database Integrity Tests (`DB`), Security & Safety Tests (`SEC`), System & Recovery Tests (`SYS`), then Playwright Execution Guide (`PW`). Create or revise one category tab at a time and stop for explicit owner review/confirmation before proceeding to the next. Use the exact 11-column template in `docs/manual-testing.md`; new steps start Not run with blank evidence/tester/date. Retain the existing Start Here/baseline records while this migration is staged.
- The dedicated Playwright Execution Guide is mandatory when its review stage is authorized. Use `PW-xxx` rows in the same 11-column structure for exact guarded PowerShell commands, expected windows/output/pass-fail signals and environment/fixture prerequisites: UI mode, headed desktop/mobile runs, spec/grep targeting, Inspector debug, Trace Viewer, and screenshot/video artifact review. Verify commands against the installed configuration; a planned guide is not an executed Playwright pass.
- The owner's primary development launch is `npm start`, fixed to loopback port 3000. Keep production-mode review (`start:production`) and automated production-mode serving (`start:test`, port 3100) explicit. README is the current command/URL index; update linked manual instructions when launch behavior changes.
- Maintain `docs/tech-stack.md` as the single current technology-stack inventory and visual diagram. Other guides link to it while retaining their own operational procedures and design rules. Approved technology/version/topology/status changes must update it, its reviewed date, affected instructions and dated history together. Verify against executable manifests, lockfiles and configuration; preserve historical records and manual results. See its maintenance section and `docs/agent-workflow.md`.
- Keep a dated, reviewable history for every phase and iteration. Before each handoff, the orchestrator updates `docs/progress.md` and the applicable phase/iteration record with finished work, changed files, validation evidence, decisions, remaining work/blockers and owner acceptance status. Preserve prior entries; distinguish planning, implementation, verification and acceptance. Agents supply history notes within their role boundaries; one assigned writer maintains shared history.

See `docs/agent-workflow.md` for task packets, role handoffs and independent review, and `docs/security.md` for operational isolation requirements.
